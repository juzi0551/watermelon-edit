# 校对角色识别前置化 设计方案 (v1.1)

> 目标：在每次校对窗口 LLM 调用前，增加一次独立的「角色识别」前置步骤，解决当前 `context.py` 仅注入前 20 个角色的信息不足问题，并用 **ID 确定性匹配** 根治角色节点分裂。
>
> 变更记录：v1.1 吸收评审结论 —— ① 延迟缓解改为「可配快模型」；② 150 角色上限先不做，仅加廉价逃生阀；③ 新角色由 Stage 0 带 aliases/first_appear_idx、Stage 1 单列注入建档；④ 幻觉 id 记入响应内内存映射；⑤ Stage 0 缓存后置为远期优化。v1.1 修订：移除自适应跳过（角色数少时同样走 Stage 0，流程恒一）。

---

## 一、背景与问题

当前流程（单次窗口调用）：

```
窗口文本 + 「已登记人物画像」(top 20 by first_appear_idx) → LLM 主校对 → proofer 解析落库
```

已知问题：

1. **注入范围过窄**：`context.py:35` 取 `nodes[:20]`（按首次登场序），窗口在书后段时，活跃角色大概率不在列表内；而 prompt 强约束 relationship 的 from/to 使用「标准主姓名」，模型信息不足 → 用别名/变体 → 依赖 alias_map 兜底补救而非根治。
2. **无法单次预判相关角色**：语义相关（代词、回忆、幕后提及）无法用子串共现可靠识别，因此此前讨论否决了「仅靠共现筛选」。
3. **画像漂移风险**：全量注入时模型可能顺手改动未登场角色的全局画像。
4. **匹配脆弱**：落库靠 name → alias 文本匹配，同名/别名冲突时易错。

## 二、方案总览

在 `Stage 1 主校对` 之前插入 `Stage 0 角色识别`，形成两阶段流水线：

```
Stage 0: 角色识别（新，轻量 LLM 调用）
  输入 = 窗口文本 + 全量已登记角色表（compact: id/name/aliases/role，不含 description）
  输出 = appearing_character_ids[] + suspected_new_characters[]（新角色含 aliases + first_appear_idx）

Stage 1: 主校对（改造）
  上下文注入 = 仅 appearing_character_ids 对应角色的全量 description（≤100字）
           + 【本段怀疑新出现角色】单列注入（姓名 + 别名）
  输出结构  = character_updates / relationship_events 携带 id（冗余 name）
  落库匹配  = id → name → alias → 新建（四段匹配链，含幻觉 id 响应内映射）
```

关键原则：

- **Stage 0 只做识别，不做画像合成** → 任务简单，可配便宜/快模型，输出极小（几个 ID）。
- **全量描述只在主校对出现一次**（识别出的角色），token 可控。
- **主名信息始终完整**（Stage 0 注入全量 compact 表），无论识别准确与否，模型都看得到全部主名。
- **ID 匹配确定性落库**，文本匹配降级为兜底。

## 三、详细设计

### 3.0 Stage 0：角色识别

**输入**（compact 角色表，来自 `get_characters(project_id)`，剔除 description）：

```
【已登记角色表】
[a1b2c3d4e5f6] 智星（别名：老大/小石头）[主角]
[78f9a1b2c3d4] 陆凡 [配角]
...
```

**逃生阀**：compact 表角色数 > 200 时，自动去掉 aliases 列（仅留 `id + name + role`），防极端 token 膨胀。

**System Prompt（新增常量，建议入 settings 表可覆盖）**：

```
你是一名中文小说角色识别器。给定【已登记角色表】与【待校对窗口文本】，识别窗口中登场或被提及的角色。

规则：
1. 严格基于文本。角色直接出场、被称呼、以代词/回忆/间接方式提及，均视为登场。
2. 仅输出确实出现于文本中的角色；未出现的一律不得列入。
3. 若文中出现角色表中不存在的人名，记入 suspected_new_characters，必须给出 aliases（文中出现的其他称呼）与 first_appear_idx（首次出现段落索引）。
4. 识别为登场的已登记角色，输出其 [id] 前缀中的 id，id 必须逐字复制自角色表。
5. 严禁输出任何解释、Markdown 代码块标记，只返回纯 JSON：
{
  "appearing_character_ids": ["a1b2c3d4e5f6", "..."],
  "suspected_new_characters": [{"name": "...", "aliases": ["..."], "first_appear_idx": 3}]
}
```

**用户侧输入**：`【已登记角色表】` + `【待校对窗口文本】`（复用 `build_proofread_user_text` 的 `[idx] text` 格式）。

**实现**：`proofer.py` 新增 `identify_window_characters(project_id, window_paras, model_id) -> tuple[list[str], list[dict]]`。

### 3.1 Stage 1：主校对上下文注入改造

`build_project_context_parts(project_id, current_paragraph_idx, appearing_character_ids=None)`：

- 传入 `appearing_character_ids` 时，只注入集合内的角色，格式改为：

  ```
  [a1b2c3d4e5f6] 智星（别名：老大/小石头）[主角] 全局画像：沿河村少年……
  ```

- 未传入（识别失败回退）时，维持现状 `nodes[:20]` 逻辑。
- 标题仍为「【已登记人物画像】」。

### 3.2 主校对 Prompt 修改（`DEFAULT_SYSTEM_PROMPT_PROOFREAD`）

**新增单列注入块**【本段怀疑新出现角色】（来自 Stage 0 输出）：

```
【本段怀疑新出现角色】
· 看瓜老人（别名：老瓜头）
· 剑圣（未提别名）
```

**第 1 条 character_updates**：

- 新增字段 `id`：若角色在【已登记人物画像】中，输出其 `[id]` 前缀 id（逐字复制）；新角色（【本段怀疑新出现角色】）不填 id。
- 新增约束：**仅允许更新【已登记人物画像】中列出的角色，以及【本段怀疑新出现角色】；未列出的已登记角色严禁输出。**
- 新角色：由主校对一次性合成初始 `description`（全局画像）与 `delta_summary`（当段履历）。

**第 2 条 relationship_events**：

- `from` / `to` 各携带 `id`（可选，冗余）与 `name`。id 优先用于落库匹配。
- 引用角色同样受「已登记人物画像」清单约束。

**JSON 示例更新**：`character_updates` 增加 `"id": "a1b2c3d4e5f6"` 字段示例。

### 3.3 落库匹配链（`proofer.py` 改造）

`_extract_and_save_character_events` 中 `_resolve_char_id`，四段匹配：

```
1. id 存在且 character_id 在 characters 表中 → 直接使用
2. 否则 name 命中 char_map → 使用
3. 否则 alias 命中 alias_map → 使用
4. 均失败 → upsert_character 新建，并登记回 char_map
```

**幻觉 id 响应内映射**：

- 若模型输出了 DB 中不存在的 id（幻觉），立即降级按 name 匹配，并把「幻觉 id → 真实 character_id」写入本次响应作用域内的 `fake_id_map`。
- 同响应内后续 relationship_events 引用同一幻觉 id 时，先查 `fake_id_map`，命中即用真实 id，不重复匹配/新建。

### 3.4 流程编排（`proofread.py` 改造）

在 `_proofread_job` 两处窗口循环（continue / selection）中：

```
1. 窗口文本就绪后，调 identify_window_characters（Stage 0）
2. 用识别结果构建 system_prompt（Stage 1）
3. 主校对调用不变，但 system_prompt 携带 appearing_character_ids + suspected_new_characters
```

**异步不阻塞**：识别为独立 `await call_llm`，完成后才进入主校对。

### 3.5 失败回退与边界

| 场景 | 行为 |
|---|---|
| Stage 0 识别调用失败（LLM 错误/超时） | 记录日志，回退 `nodes[:20]` 注入，校对不中断 |
| Stage 0 JSON 解析失败 | 同上回退 |
| Stage 0 返回空 appearing_ids | 回退 top-N |
| 主校对输出幻觉 id（表中不存在） | 走 3.4 的 fake_id_map + name/alias 匹配链，不新建 |
| 主校对输出 id 与 name 不一致 | 以 id 优先（id 更确定），但若 id 查无此人则回退 name |

### 3.6 配置项（settings 表，新增）

| key | 默认 | 说明 |
|---|---|---|
| `proofread_identifier_enabled` | `1` | 是否启用 Stage 0；0 时完全走旧逻辑 |
| `proofread_identifier_model` | 空 | Stage 0 使用的模型；空则复用主校对 `req.model`（不强配，单模型环境安全） |

## 五、性能与成本

- 每窗口新增 1 次 LLM 调用。输出约 1 个 ID 列表（<50 token）。
- 主要成本为窗口文本的重复输入（与主校对相同体量）；`proofread_identifier_model` 可配更便宜/更快的模型。
- 100 段窗口估算：主校对约 4-6k token；Stage 0 约 4-6k（compact 表 ≈2k + 窗口文本 4k）+ 输出可忽略。总量约为当前单次的 1.2~1.4 倍，换来识别精度与画像稳定性。
- **延迟缓解手段**：① 快模型（可配）；② 识别输出极小，首 token 快。

## 六、测试计划

1. `identify_window_characters`：构造识别结果 JSON 解析正确性。
2. proofer 四段匹配链：id 命中 / 幻觉 id 响应内映射 / name 缺失回退 alias / 全失败新建。
3. 注入过滤：appearing_character_ids 注入仅含清单角色；缺省回退 top-N。
4. Stage 0 失败回退：mock 识别失败，主校对仍走通且落库正常。
5. 回归：`pytest backend/app/tests/`、`npm --prefix frontend run build`。

## 七、评审结论记录

| # | 评审问题 | 结论 |
|---|---|---|
| 1 | 新角色处理 | **采纳**：Stage 0 输出 aliases + first_appear_idx；Stage 1【本段怀疑新出现角色】单列注入建档 |
| 2 | 新角色 aliases 注入 | 同 #1 |
| 3 | compact 表分页/截断 | **先不做 150 上限**，仅加「>200 去 aliases」逃生阀 |
| 4 | id 与 name 冲突口径 | **采纳**：id 优先，幻觉 id 立即降级 name 并记 fake_id_map，不新建 |
| 5 | Stage 0 结果缓存 | **后置为远期优化**：收益有限且需登记表指纹参与 key，暂不实现 |
| 6 | 延迟累加 | **采纳（改造）**：可配快模型缓解；不引入自适应跳过（流程恒一，降低复杂度） |
