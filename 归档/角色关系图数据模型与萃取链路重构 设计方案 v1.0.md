# 角色关系图数据模型与萃取链路重构 设计方案 (v1.0)

> 目标：把图上「边」的语义从**关系事件**重构为**关系状态**，使关系图符合行业最佳实践（类型化加权图 + 时序快照），并修复「血缘等持久关系只写在 description、不成边」的萃取缺口。
>
> 范围：仅以新项目 `06ea12e621ca` 为准；其余项目为历史数据，不在本次改造范围，也不作为设计依据。

---

## 一、背景与问题（以项目 06ea12e621ca 为准）

当前数据现状：

- 9 个角色、5 条边，无重复对、无类型冲突（数据本身干净）。
- **缺口**：智星/铜锁/哈呼 三个角色的 description 均写明「三兄弟」（老大/老二/最小），铜铃的 description 写明「铜锁的弟弟，年仅两岁」——但 `character_relationships` 表中**均无 family 边**（仅有一条 铜锁↔哈呼 friend）。

根因（三层）：

1. **边的语义是"事件"而非"状态"**：一条边 = LLM 某窗口输出的一条 `relationship_events`（"第 N 段发生了互动"）。铜锁↔哈呼 有"互动事件"所以有线；血缘这种**静态持久关系**没有对应事件，所以无线。
2. **萃取规则只对"事件"触发**：prompt 说「文中**发生**关系建立/转变时」输出 relationship_events。写在 description 里的"弟弟/兄弟"不是事件，模型不会自动补边。
3. **模型看不到已有关系**：注入上下文只有角色画像（description），没有已存在的边信息，模型既不知道哪些边已有，也无从"确认/更新"。

## 二、设计原则：行业最佳实践映射（不造轮子）

| 设计决策 | 对应最佳实践 | 说明 |
|---|---|---|
| `relationship_events` 追加写入，作为唯一事实源 | **Event Sourcing** | 事件日志 append-only，不删不改，是可靠的事实记录 |
| 图 = 事件日志的派生投影 | **Projection / Read Model**（CQRS） | 图不是独立数据，而是按需从事件折叠出的只读投影 |
| 边带有效时间，支持"截至第 t 段"快照 | **Temporal / Valid-Time 建模** | 一条边从"确立段"起持续有效，直到被更新 |
| 一对角色一条边，类型 + 权重 | **类型化加权图**（图数据库惯例） | typed + weighted + undirected edge，关系图的标准形态 |
| 关系演进而非删除，保留全部历史事件 | **SCD Type 2**（缓慢变化维度） | 事件全量保留，当前状态取最新一条 |

核心思想一句话：**事件是日志，关系是状态，图是投影。** 全部复用成熟模式，不改存储结构、不新造模型。

## 三、目标数据模型

### 3.1 事件日志（保持不变）

`character_relationships` 表维持现状，作为关系事实的唯一来源：
LLM 每窗口输出的 `relationship_events` → `insert_relationship` 追加一行。**读取路径之外零改动。**

### 3.2 状态投影（查询时派生，`graph_engine` 层）

对每一对角色 `(u, v)`（无向，min/max 归一），折叠全部事件得到：

| 字段 | 来源 | 语义 |
|---|---|---|
| `type` | 该对 **`paragraph_idx` 最大**事件的关系类型（同段取 `created_at` 最新） | 当前/截至 t 的主导关系类型 |
| `strength` | 该对事件总数 | 关系强度（连线粗细依据） |
| `established_at` | 该对事件的最小 `paragraph_idx` | 关系确立段（边生效起点） |
| `last_seen` | 该对事件的最大 `paragraph_idx` | 最近一次互动段 |

### 3.3 快照语义（Valid-Time）

在快照时刻 t，边 `(u,v)` 存在 ⟺ 同时满足：

```
① u、v 均已登场（first_appear_idx <= t）
② 该对已确立关系（established_at <= t）
```

即：一条边从"确立段"起**持续显示**（血缘/师徒/结拜都是持久关系），类型随最新事件反转，不再随事件逐条堆叠。

## 四、实施改动（三层）

### 层 1（核心）：`graph_engine.py` 投影层

- 现有逻辑：读事件 → 过滤已删段落 + `paragraph_idx <= upto` → 返回**原始行**。
- 改为：过滤后 → **按对聚合去重**（每对一条边）→ 挂 `type / strength / established_at / last_seen` → 剔除"端点未登场"的边（端点 `first_appear_idx > upto`）。
- 中心度/Louvain 聚合逻辑已存在（`edge_counts`），投影层与其复用同一份按对聚合，**输出形态与前端兼容**（仍返回 `nodes/edges`），前端零改动。
- 类型归一：投影时 `ally → friend`（与 proofer 对新数据的归一化一致，消除存量旧枚举）。

### 层 2：prompt 语义改为「关系状态声明」（`DEFAULT_SYSTEM_PROMPT_PROOFREAD`）

- `relationship_events` 定位从"关系事件"改为**"关系状态声明"**：对**本段出现**且存在明确关系的每对角色，声明其**当前关系类型**（含血缘/师徒/结拜/敌对等持久关系）。
- **强制约束**：凡在 `description` / `delta_summary` 中揭示了与既有角色的明确持久关系，**必须同时**输出一条对应 `relationship_events` 声明，二者不得只落一处。
- 类型枚举保持 `friend / enemy / family / lover / neutral` 不变；语义改为"截至当前的关系类型"。

### 层 3：注入已有关系摘要（`context.py`）

- Stage 1 上下文新增【现有关系摘要】区块，内容来自层 1 投影的当前状态：

  ```
  【现有关系摘要】（已登场角色）
  • 智星 —family→ 智星爸爸（确立于第 194 段）
  • 铜锁 —friend→ 哈呼（确立于第 292 段）
  ```

- 模型基于摘要做**新增 / 变更 / 确认**，而非每次从零猜测；血缘等持久关系一旦被确认即补边。
- 摘要仅覆盖**当前窗口已登场角色**之间的边（与画像注入范围一致，控制 token）。

## 五、快照查询逻辑（伪代码）

```
build_projection(project_id, t):
  1. events = SELECT * FROM character_relationships
             WHERE project_id=? AND paragraph_idx<=t
             AND 关联段落未删除(JOIN paragraphs, is_deleted=0)
  2. 按对分组 (pair = (min(id), max(id))):
       established_at = min(paragraph_idx)
       last_seen      = max(paragraph_idx)
       strength       = count(*)
       type           = 该对 paragraph_idx 最大的事件的 relation_type
                        （同 paragraph_idx 按 created_at 取最新）
  3. 边集合 = { pair: 两端点 first_appear_idx <= t }（端点未登场则剔除）
  4. 输出 nodes + edges(pair, type, strength, established_at, last_seen)
```

## 六、边界与回退

| 场景 | 处理 |
|---|---|
| 存量 `ally` 事件 | 投影层归一化 `ally→friend`，不改数据 |
| 无事件但 description 有血缘事实 | 投影层无法自愈，靠层 2/3 在后续校对中补边 |
| 同一对类型反转（friend→enemy） | 投影取最新，边类型随剧情演进变化（符合快照语义） |
| 关系"结束"（解除/死亡） | 本域暂不支持"边消失"；确立后持续，符合长篇故事常态，后续如需再引入"终止事件" |
| Stage 0 识别失败 | 沿用现有回退（top-N 注入），不影响投影层 |

## 七、存量数据

- **无需迁移**：事件日志原样保留，投影层"改读不改写"。
- 项目 `06ea12e621ca` 现有 5 条边经投影后形态不变；缺失的「三兄弟」「铜锁↔铜铃」边，在层 2/3 生效后通过**重校相关段落**补齐（description 事实 → relationship_events 声明 → 落库 → 投影成边）。

## 八、测试计划

1. **投影去重**：同一对多次事件 → 输出 1 条边，`type` 取最新、`strength` 计数正确。
2. **快照**：`established_at <= t` 才出现；端点未登场（`first_appear > t`）的边被剔除。
3. **类型反转**：friend→enemy 两事件，t 位于二者之间/之后时边类型分别为 friend/enemy。
4. **prompt 强制边**：mock LLM 在 description 写"弟弟"同时输出 family 声明 → 落库成边。
5. **注入摘要**：已有边出现在 Stage 1 上下文【现有关系摘要】中。
6. **回归**：`pytest backend/app/tests/`、`npm --prefix frontend run build`。

## 九、待评审问题

1. **投影实现位置**：Python 层（复用现有 JOIN 过滤与聚合）vs SQL 窗口函数（`ROW_NUMBER() PARTITION BY pair`）。推荐 Python——改动最小、逻辑可单测；SQL 窗口函数 SQLite 3.53 已支持，但侵入现有查询。
2. **strength → 边宽映射**：线性归一化 vs 对数归一化（防少数高频对把边宽顶爆）。
3. **是否需要"确认机制"**：模型重复声明同一对关系时，用"最新声明为准"即可，不引入额外去重状态机（保持简单）。
4. **已登场角色摘要的 token 上限**：登场角色较多时，摘要是否需要截断/按 strength 排序截取 top-N。
